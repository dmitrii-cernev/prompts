## Implementation posture

This is **an adaptation of an existing implementation, not a greenfield loader**. Most of the required plumbing—including record decoding, stream/batch handling, domain mappings, endpoint configuration, retry behavior, and historical alias support—is expected to already exist.

Make the smallest coherent change that:

- adapts the existing decoder/mapping to the new `idArray` input format;
- narrows alias selection to CCSID;
- enables/restores the already-supported alias API write path; and
- preserves the mature segment flow and infrastructure.

Before adding any new model, codec, client, batching abstraction, or service path, locate and reuse the existing equivalent. Prefer modifying or re-enabling existing code over replacing it. Do not redesign the loader unless the current repository proves the old abstractions cannot support the new format.

## Objective

Modify the existing Customer Hub (CHUB) NAM segment-file loader so that it:

1. reads CCSID entries from each record's `idArray`;
2. maps each CCSID value as an alias of the enclosing record's CCID;
3. sends the resulting mappings through the ID-linkage bulk aliases API so they are persisted; and
4. leaves the existing segment-loading behavior intact.

This task is intentionally narrow. Do not broaden it into generic alias ingestion or historical-data cleanup.

## Required source-to-alias mapping

For each input record and each `idArray` entry whose `type` is `CCSID`:

```text
record.ccid       -> ID to resolve / parent ID of the alias mapping
entry.value       -> aliasId
"CHUB_CCSID"      -> aliasOrigin
"NAM"             -> region
```

Example input shape:

```json
{
  "ccid": "C-100",
  "segment": ["WEALTH"],
  "idArray": [
    { "type": "CCSID", "value": "CS-900" },
    { "type": "PartnerID", "value": "P-42" }
  ]
}
```

Conceptual mapping result:

```json
{
  "id": "C-100",
  "aliases": [
    {
      "aliasId": "CS-900",
      "aliasOrigin": "CHUB_CCSID"
    }
  ],
  "region": "NAM"
}
```

The conceptual result is not necessarily the exact HTTP wire model. Use the repository's endpoint/client domain types and codecs.

## Input facts

A supplied decoded delta file is JSON Lines, with one object per line. Visible records contain:

- `ccid`;
- `segment` array;
- `idArray` containing `{type, value}` objects.

Observed ID types include:

- `CCSID`;
- `CIN`;
- `GCIFID`;
- `RMID`;
- `PWM_CLIENT_ID`.

Some records contain **multiple CCSID entries for one CCID**, as well as multiple entries of other types. Do not assume there is at most one CCSID.

## In scope

- Adapt the existing source-record decoder/model from the older fixed-field format to the new `idArray` format, reusing current decoding infrastructure.
- Select CCSID entries using the existing alias-expansion/mapping path where possible.
- Map CCSID values to `CHUB_CCSID` aliases under the enclosing CCID.
- Submit the mappings to the ID-linkage aliases bulk endpoint.
- Use region `NAM`.
- Support multiple CCSID values for one CCID without arbitrarily selecting only the first.
- Preserve existing segment decoding, mapping, submission, retries, and behavior.
- Update existing tests and add only the focused cases not already covered.
- Reuse established batching, effect handling, endpoint clients, retries, logging, and configuration rather than creating parallel implementations.

## Explicitly out of scope

Do **not**:

- delete, drop, migrate, or otherwise clean up existing alias rows;
- process non-CCSID `idArray` types as aliases;
- map account-level fields such as `accountArray.cltId`;
- implement generic `CHUB_<type>` alias support for every identifier type;
- modify GFCID/GCIFID/CLTID/PWMID historical data;
- change existing segment semantics except where mechanically necessary to adapt the shared source decoder or service flow;
- replace working loader infrastructure with a new pipeline;
- duplicate existing endpoint clients, domain mappings, retry helpers, or codecs;
- introduce `replace` or `replace-scope` deletion behavior without clear existing repository evidence and explicit requirement support.

## Known aliases endpoint

The Swagger screenshot shows:

```http
POST /customers/customerRelationship/partyResolution/clientData/v1/private/aliases/bulk
```

Visible request controls include:

- required request UUID header;
- `region` query parameter;
- mandatory `target[]` query parameter, represented as `store:origin` and exemplified by `individuals:CHUB`;
- `writeMode`: `add`, `replace`, or `replace-scope`, with `add` as the documented default;
- `scopeOrigin[]`, applicable to `replace-scope` only;
- `resolution`: `direct` or `joint-party`, with `direct` as the documented default;
- `audit` boolean, default false; audit mode requires alias entries to carry `aliasType`.

The displayed request-body shape is approximately:

```json
    "ids": ["string"],

        "aliasId": "string",

        "eventType": "string"
      }
    ]
  }
]
```

Do not hand-code this shape if generated or existing client models/codecs already exist.

## Individual/entity target behavior

Known behavior for the existing segment path:

- the decoded file has no individual/entity marker;
- the segment loader sends two parallel calls, one to the individual store and one to the entity store;
- if a CCID does not exist in a target schema, that target does not store the mapping.

Investigate whether the alias endpoint is expected to use the same two-target strategy. Determine the exact configured target strings from code/config/tests rather than guessing them.

Likely possibilities may resemble `individuals:CHUB` and an entity equivalent, but only repository evidence should decide the actual values.

## Behavioral decisions to derive carefully

### Multiple CCSID entries

Real decoded records can contain multiple CCSID entries for one CCID. Unless existing contracts or tests establish different semantics:

- preserve every distinct nonblank CCSID value;
- do not silently choose the first value;
- avoid duplicate alias entries for exact duplicate values within a mapping/batch.

If the current domain contract allows only one alias per origin, stop and report that conflict before inventing precedence.

### Type comparison and validation

Determine and follow the loader's established conventions for:

- exact versus case-insensitive matching of `CCSID`;
- trimming whitespace;
- blank `ccid`;
- blank CCSID value;
- absent or empty `idArray`;
- malformed entries;
- duplicate input rows.

At minimum, non-CCSID entries must not generate aliases.

### Write semantics

Cleanup is out of scope. Prefer the existing non-destructive contract used by this loader/client. The Swagger default is `add`, but verify repository configuration or historical behavior before relying on the default.

Do not use `replace-scope`. Do not add deletion behavior.

### Failure semantics

Follow existing project patterns, but ensure:

- alias API failures are not silently treated as success;
- retriable failures use established retry/backoff behavior;
- permanent failures propagate appropriately;
- `skippedIds` are logged/metricized or otherwise observable according to project conventions;
- logs do not expose customer IDs or other sensitive identifier values;
- segment/alias partial success has explicit, tested behavior.

## Expected implementation shape

The final shape will likely resemble:

```text
JSONL record
  -> decode ccid, segment, idArray
  -> preserve current segment mapping
  -> filter idArray to CCSID
  -> build CCID -> CHUB_CCSID alias mappings
  -> batch mappings
  -> call aliases bulk API for required target stores in NAM
  -> handle success, skipped IDs, retryable failure, permanent failure
```

This should be an incremental modification of the existing path. Use the repository's current abstractions and former alias-write plumbing rather than introducing a parallel architecture.

## Acceptance criteria

The implementation is complete when:

1. A valid `CCSID` entry produces an alias mapping for the enclosing CCID.
2. `aliasId` equals the CCSID value.
3. `aliasOrigin` equals exactly `CHUB_CCSID`.
4. Region equals `NAM`.
5. Multiple CCSID values are handled according to the confirmed contract without silently losing values.
6. Non-CCSID and account-level identifiers produce no aliases.
7. The resulting mappings are sent through the ID-linkage aliases bulk API.
8. The aliases are targeted to the correct individual/entity stores according to established code/configuration.
9. Existing segment behavior remains unchanged.
10. No existing alias data is deleted or migrated.
11. API failures, retries, skipped IDs, and partial outcomes are handled observably and consistently with project conventions.
12. Relevant tests pass.
